# Tana-parity gap recon — 2026-07-07

Verdict: nxus's *query and inheritance data models are already more expressive than their editor UIs expose* — the three items from the lost prior-session recon (formula fields, boolean query grammar, extends config UI) partially survive scrutiny but need real correction: formula fields are a genuine full gap, boolean query grammar is **partial** (nxus already has one-level AND/OR/NOT + relation/temporal filters in the UI; the real gaps are nested groups and `path`-filter authoring), and extends config UI **already exists** in nxus — the actual gap is that it's single-parent only where Tana supports multi-parent (DAG) inheritance. The highest-leverage net-new gap found by live use of Tana is **formula/computed fields**, followed by **multi-parent supertag inheritance**. Both are data-model-level; most of the rest (query builder nesting, command palette, multi-panel navigation) are editor-UI-level and sit on top of a data model that can already represent them.

Method: read `spec/product/editor.md`, `spec/product/data-model.md`, `spec/product/vision.md`; drove the live Tana app (workspace `_RyqjL96p2A6`) via Playwright MCP through supertag configuration, field-type creation, search-node/query-builder authoring, and command palette; delegated a targeted check of nxus's actual `@nxus/workbench` `QueryBuilder` UI to a subagent to verify what's authorable today vs. only present in the JSON model.

## Top-10 ordered backlog

1. **Formula / computed fields.** Add a `formula` (or `computed`) `FieldType` whose value is derived from a small expression referencing sibling/ancestor field values (start with arithmetic + simple string ops over `node`/`nodes` references), evaluated at assembly time. **Depends on the node data model** (`libs/nxus-db`: new `FieldType` variant + an evaluator in the assembly path, `node.service.ts`) — the editor's `field-value.tsx` dispatch table just needs one more case once the model exists.

2. **Multi-parent supertag inheritance.** Change `field:extends` from a de-facto single value to a genuine multi-value property (it's already `addPropertyValue`-shaped structurally), update `assembleNodeWithInheritance`'s ancestor walk to merge across multiple parents, and fix the already-known I4 asymmetry (ancestor-walk depth vs. descendant-expansion depth) in the same pass since both touch the same inheritance code. **Depends on the node data model** (`node.service.ts:122-164,539-598`) plus a UI change to `SupertagDetailView`'s Extends pill to allow more than one.

3. **Inline mention backlinks.** Define how a rich-text/plain-text reference to another node is stored (likely: parse `@`-references out of `content` at write time into a new reference-kind property, or a lighter-weight extracted-mentions table) so `getBacklinksServerFn` can finally emit non-empty `inline-mention` groups. This closes a DRIFT nxus already wrote about itself. **Depends on the node data model** — this is the one gap the current spec calls out as blocked on a model decision, not an editor limitation (`editor.md:208-212`).

4. **Query builder: nested groups + `path`-filter authoring.** Let `LogicalFilterEditor`'s "Add filter" include `and`/`or`/`not` recursively (not just simple filter types), and add a `PathFilterEditor` so `path` filters (reference-chain traversal, e.g. `Hat.Color = "Red"`) are authorable, not just displayable. **Editor-UI-level only** — `QueryDefinition` already supports arbitrary recursion and `path` filters; this is purely `libs/nxus-workbench/src/features/query-builder/` work (`add-filter-menu.tsx`, `filter-chip.tsx`).

5. **Supertag base-type.** Add an optional `field:base_type` (enum: day/week/task/person/event/…) on supertag definition nodes, and let a small number of engine behaviors (e.g. calendar apps' day/week handling, recall's card handling) key off it instead of hardcoded `SYSTEM_SUPERTAGS` identity checks. **Depends on the node data model** (new schema attribute + a few consumers), but is additive and low-risk since it doesn't change existing semantics.

6. **Unify and fix the command palette.** Collapse Cmd+S (search) and Cmd+K (commands) into one global, always-available palette (search nodes, run commands, navigate) matching Tana's single-entry-point model, and fix the four currently-failing Cmd+K e2e tests (DRIFT §11) as part of the same work rather than leaving it broken underneath a redesign. **Editor-UI-level** (`command-palette.tsx`, `node-command-palette.tsx`, `outline-editor.tsx:358-412`).

7. **Multi-panel / stacked side-panel navigation.** Let "configure this" actions (supertag config, field config) open a panel that stacks beside the current view instead of navigating away from it, with a "close this panel" affordance — this directly serves nxus's "quick in-place configuration without leaving the outline" principle already stated for the inline `SupertagConfigPanel` (`editor.md:170`), generalized beyond just that one popover. **Editor-UI-level** (new panel-stack primitive in `apps/nxus-editor`).

8. **Supertag schema tiers + default child supertag.** Split a supertag's field schema into "always shown" vs. "available on demand" (distinct from the existing `hideWhen` visibility axis, which is about runtime emptiness, not discoverability), and add a `field:default_child_supertag` so nodes created under a tagged node inherit a tag automatically. **Data-model-level** (schema attribute) **+ editor UI** in `SupertagConfigPanel`/`SupertagDetailView`.

9. **Field auto-initialize from ancestor.** A per-field config flag that, on node creation, copies the value of the same field from the nearest ancestor that has it set (useful for e.g. a "project" field cascading down a task tree). **Small data-model addition** (a fill-rule evaluated at `createNode` time) **+ editor UI** (one toggle in field config).

10. **Multiple named filtered sub-views per node.** Let a node support several saved, independently filtered/sorted "view tabs" (like Tana's per-tag menu items) instead of the current one-view-per-node model, reusing the existing `field:view_as`/`field:view_config` machinery but making it array-valued. **Editor-UI-level primarily**, though the config storage shape needs to move from a single hidden field pair to a list.

### Data-model vs. editor-UI dependency, at a glance

- **Blocked on the node data model** (schema/assembly/query-engine changes in `libs/nxus-db`): #1, #2, #3, #5, #8 (schema tier + default-child attribute), #9 (fill-rule).
- **Editor UI only** (data model already sufficient): #4, #6, #7, #10.

## Surprising findings worth flagging

- **The "known prior recon top-3" doesn't survive contact with the live app unchanged.** Boolean query grammar and extends-config-UI are not missing — nxus already has one-level AND/OR/NOT plus relation/temporal filters in `@nxus/workbench`'s `QueryBuilder`, and already has an extends-config UI in both `SupertagDetailView` and the inline `SupertagConfigPanel`. The real, narrower gaps are: nested groups + `path`-filter authoring (query), and single- vs. multi-parent (extends). Formula fields is the one item that survives as a clean, total gap.
- **Formula fields in Tana are a semi-hidden feature**, not a documented field type: there is no "Formula" entry in the New Field type menu (`Plain, Options, Options from supertag, Date, Number, Tana User, Url, E-Mail, Checkbox`); it's invoked via an undocumented `Set formula` command on an existing field, and values are Lisp-like function nodes with children as arguments. Any nxus implementation should feel free to make this a real, discoverable field type rather than copying Tana's hidden-feature UX.
- **Tana supports genuine multi-parent (DAG) supertag inheritance**, confirmed live: `#S:knowledge` simultaneously extends `#Relationship` and `#w/content-tag`. nxus's data model and its own DRIFT register (I4) both assume a single-parent chain — this is a bigger data-model change than it first looks, since it also changes what "ancestor walk" and "descendant expansion" mean.
- **Tana treats supertags as automation anchors**: per-supertag "Trigger commands on events" (on added/removed/checked/unchecked) turns tagging itself into a workflow trigger, tightly coupling schema and automation in a way nxus's more general reactive layer (`spec/tech/reactivity.md`, not audited here) may or may not already cover — worth a follow-up read before deciding whether this is a gap or already-served-differently.
- **Tana's query authoring is a mini textual language embedded in the outline** (`>` inserts fields, `@` inserts node/tag references, plain text = keyword search, live-compiled to a readable boolean expression, with an explicit Run-once vs. live toggle) rather than a form-based filter builder. nxus's `QueryBuilder` is form-based throughout — this is a UX-paradigm difference worth a deliberate product decision, not just a feature-parity checklist item.
